Start the server, then call a function from Node with the generated client:

```bash
npx forst generate .
npx forst dev -root ./my-service -port 6320
export FORST_BASE_URL=http://localhost:6320
```

```typescript
import { $main } from "@forst/gen/main";

await $main.Echo({ message: "hello" });
```

**`forst dev`** watches your `.ft` tree, recompiles on change, and exposes a stable HTTP contract for tooling and Node clients. Full call and failure docs: [Call Forst from Node](/interop/node/call-forst).

## Generated client

Editing a `.ft` file regenerates the TypeScript client so the editor stays in step with the server. In development, sidecar **`watchGenerate`** defaults to **true** and runs `forst generate` after a debounced reload. You can also run a standalone watcher:

```bash
npx forst generate --watch .
```

`forst clean` removes `.forst/client` with the rest of `.forst`. The next `forst generate` (or `postinstall`) restores `@forst/gen`.

See [CLI reference § Generate configuration](/workflow/cli#generate-configuration) for `outDir`, `packageName`, and related fields.

## Endpoints

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/health` | Server liveness |
| `GET` | `/functions` | List invokable functions |
| `POST` | `/invoke` | Execute a function with JSON payload |
| `GET` | `/types` | Type information for tooling |
| `GET` | `/version` | Compiler version and **`contractVersion`** |

The invoke envelope uses JSON request/response bodies. The same contract applies to the built-in HTTP server in a compiled binary. See [Call Forst from Node](/interop/node/call-forst).

Clients should check **`contractVersion`** on `/version` when upgrading the compiler.

## Configuration

Share discovery rules with **`forst generate`** via **`ftconfig.json`**:

```json
{
  "server": {
    "port": "6320",
    "cors": true
  },
  "dev": {
    "logLevel": "info",
    "watch": true,
    "hotReload": true
  },
  "files": {
    "include": ["**/*.ft"],
    "exclude": ["**/node_modules/**", "**/.git/**"]
  }
}
```

`files.include` and `exclude` control which `.ft` files are watched and compiled. Globs resolve from the **ftconfig boundary root**. Each directory holds one Forst package name, matching Go layout rules.

### Runtime profile (embedded / host mode)

When `server.embedded` or `bridge.hostMode` is true, `forst dev` compiles and runs your entry `.ft` (same pipeline as `forst run`) instead of the per-invoke HTTP executor.

By default, `dev.hotReload` is **true** in `ftconfig.json`, so the CLI watches `.ft` files under `-root`, recompiles on change, and restarts the generated program. Set `"dev": { "hotReload": false, "watch": false }` for a one-shot compile+run (no file watching).

Compile errors during reload are printed to **stderr**. The watch loop keeps running; if a previous build was already running, it stays up until a successful recompile replaces it.

`@forst/sidecar` spawn mode is an alternative: it restarts the whole `forst dev` child on `.ft` changes and can run **`watchGenerate`** after those reloads.

## When to use dev vs pure Go

| Scenario | Approach |
| --- | --- |
| New greenfield service | Compile to Go, deploy directly |
| Local iteration from Node or scripts | **`forst dev`** plus `@forst/gen` |
| Production Node → Forst | Built-in HTTP server + **`FORST_BASE_URL`** — see [Call Forst from Node](/interop/node/call-forst) |
| Full stack type sync | **`forst generate`** in `postinstall` / CI |

## Caveats

**`forst dev`** is **experimental**. Pin compiler versions. Run integration tests in your pipeline.

### Same port convention

Point **`FORST_BASE_URL`** at the server you actually run. Executor profile and embedded profile often use different defaults (`6320` vs `6321`). See [Call Forst from Node § Caveats](/interop/node/call-forst#caveats).

### Providers in Go host

Invoke carries request payloads only. Wire **`with`** blocks in Go before exposing handlers. See [Providers § Caveats](/language/providers#caveats).
