Forst can call functions from your existing TypeScript and JavaScript modules.
This lets you move backend code to Forst one part at a time. Working Node code
can stay in place while new code compiles to Go.

To call Forst from Node instead, see [Call Forst from Node](/interop/node/call-forst). For shared types only, see [Generate client types](/interop/node/generate-types).

## Your first call

Start with an ordinary TypeScript module at `legacy/payment.ts`.

```typescript
export function create(amount: number, currency: string): { id: string } {
  return { id: "pay_1" };
}
```

Import that module in Forst and call the export.

```ft
import "./legacy/payment" js

func main() {
  result := payment.create(100.0, "USD")
  ensure result is Ok()
  println(result.id)
}
```

The postfix **`js`** marker tells Forst that this path points to a JavaScript module. The compiler checks the function name, arguments, and return value. The call returns a `Result`, so `ensure result is Ok()` handles failures before you use the value.

At runtime, the compiled app starts a local bridge process when it first needs one. Calls stay on the same machine. If your program does not use a JS import (`import "./path" js`), the compiled binary does not need JavaScript.

## Set up JS bridge interop

Install Forst first. See [Installation](/installation) for npm and native options.

Install the runtime package.

```bash
npm install @forst/runtime
```

JS bridge interop uses the same `ftconfig.json` boundary as `forst dev` and `forst generate`. Include your TypeScript files and enable the runtime.

```json
{
  "files": {
    "include": ["**/*.ft", "**/*.ts", "**/*.tsx"],
    "exclude": ["**/node_modules/**", "**/.git/**"]
  },
  "bridge": {
    "enabled": true,
    "importPolicy": "explicit",
    "runtimeEnabled": true
  }
}
```

Forst only loads modules opted in with the postfix **`js`** marker. Plain imports never start the JS bridge.

## Import a module

Use the file name as the local name, or choose an alias.

| Form | Example | Local name |
| --- | --- | --- |
| File name | `import "./legacy/payment" js` | `payment` |
| Alias | `import checkout "./legacy/api/checkout" js` | `checkout` |

You can also place JS imports inside a grouped import.

```ft
import (
  "strconv"
  "./legacy/payment" js
  checkout "./legacy/api/checkout" js
)

func main() {
  result := payment.create(100.0, "USD")
  ensure result is Ok()
  println(result.id)
}
```

Each import exposes the module namespace. For example, `payment.create` calls the `create` export. Your TypeScript files need no Forst annotations.

### When the file or package name is reserved

If the default local name is a Forst or Go keyword, or not a valid identifier, Forst reports an error at the import and suggests an alias.

```ft
import typePkg "./legacy/type.ts" js
import effectLib "@effect/platform" js
import my_package "@scope/my-package" js
```

Common cases.

| Path or package | Problem | Fix |
| --- | --- | --- |
| `./legacy/type.ts` | `type` is a keyword | `import typePkg "./legacy/type.ts" js` |
| `"map"` (npm) | `map` is a keyword | `import mapPkg "map" js` |
| `@scope/my-package` | hyphens are invalid in identifiers | `import my_package "@scope/my-package" js` |

Scoped npm packages such as `@effect/platform` default to the last path segment (`platform`) when that name is valid.

## Build and run

Use `build` when you want Go output for deployment. Use `run` when you want to compile and start the program in one step.

Enable embedded invoke in `ftconfig.json` before a production build.

```json
{
  "server": { "embedded": true }
}
```

```bash
npx forst build -root ./my-service -o .forst/build -- ./cmd/api/main.ft
npx forst run -root ./my-service ./cmd/api/main.ft
```

Run the binary from `manifest.json`, for example `bin/main`.

```bash
FORST_ROOT=/app /app/.forst/build/bin/main
```

Your deployed app needs a JavaScript bridge host and `@forst/runtime` when any reachable Forst package uses a JS import. Production builds default to compiled legacy modules. At compile time Forst writes esbuild bundles to `.forst/js/` under the project boundary. At runtime the compiled modules directory can live anywhere. Set `FORST_BRIDGE_MODULES_DIR` or `bridge.legacyModules.dir` when you mount or copy that tree outside the default path. In compiled mode you do not need `tsx` at runtime. Set `bridge.legacyModules.format` to `"typescript"` only when you intentionally load `.ts` or `.tsx` source files in production.

## Choose the bridge host

Configure the bridge with `bridge.host` (`node`, `bun`, or `deno` when enabled) and `bridge.legacyModules.format` (`compiled` or `typescript`). The deprecated `bridge.legacyModules.format` field maps to format for older configs (`tsx` for typescript on Node only, `none` for compiled). The deprecated `legacyModules.artifact` key and values `source` or `precompiled` are still accepted.

| Host | Module format | Runtime needs |
| --- | --- | --- |
| `node` (default) | `compiled` (default) | Node + `@forst/runtime` + compiled modules directory |
| `node` | `typescript` | Node + `tsx` + `@forst/runtime` |
| `bun` | either | Bun + `@forst/runtime` (no `tsx`) |
| `deno` | either | Deno + `@forst/runtime` when `FORST_DENO_HOST_ENABLED=1` |

Example production config.

```json
{
  "bridge": {
    "host": "node",
    "legacyModules": {
      "format": "compiled",
      "dir": ".forst/js",
      "precompile": { "outDir": ".forst/js" }
    }
  }
}
```

#### What `.forst/js` is

When you use `import "./payment.ts" js`, Forst typechecks the TypeScript source at compile time. It also runs esbuild to bundle each imported module into a standalone `.js` file. Those bundles form the compiled modules directory. By default Forst writes them under `.forst/js/` in your project. For example, `legacy/payment.ts` becomes `.forst/js/legacy/payment.js`.

At runtime the bridge loads these `.js` files with dynamic import. It does not execute your original `.ts` files, and it does not reuse output from Vite or webpack. Forst generates its own bundles to ensure stable paths and module shapes.

#### Shipping compiled modules with `forst build -o`

`forst build -o` creates the Go binary and `manifest.json` without copying `.forst/js` to the output directory or next to the binary. Treat the compiled modules tree as a separate deploy artifact. Copy or mount it wherever your deployment requires.

When the program uses bridge imports, `manifest.json` records `compiledModulesDir` (usually `.forst/js`, relative to the project boundary) so you know which directory the runtime expects.

#### Telling the runtime where the bundles live

The bridge resolves compiled `.js` module IDs on disk using this order:

1. `FORST_BRIDGE_MODULES_DIR` environment variable (absolute path on the host)
2. `bridge.legacyModules.dir` in `ftconfig.json` (relative to the project boundary, or absolute)
3. Default: `{FORST_ROOT}/.forst/js`

`FORST_BRIDGE_MODULES_DIR` is the option for split layouts. Set it when the bundled files live outside the project boundary, for example on a shared volume or in a sidecar container.

```bash
FORST_ROOT=/app \
FORST_BRIDGE_MODULES_DIR=/mnt/forst-modules \
/app/.forst/build/bin/main
```

In that example, `/mnt/forst-modules/legacy/payment.js` is the file the runtime loads for module ID `legacy/payment.js`. The Go binary location does not matter. Forst never searches for `.forst/js` beside the executable.

Set `FORST_ROOT` to the project boundary where `ftconfig.json` lives. That path is used for configuration, TypeScript source mode, and socket files under `.forst/`. It stays separate from the compiled `.js` bundle path when you set `FORST_BRIDGE_MODULES_DIR`.

### Bridge host E2E testing

CI runs Bun and Deno bootstrap tests via `task test:bridge-host-e2e` from the repo root. Locally, install Bun and Deno matching `.deno-version` on your `PATH`, build `packages/runtime`, then run that task. Without both hosts, Go tests skip instead of failing.

Most projects should use bootstrap mode. It starts a small bridge process for Forst calls. Host mode is for apps that need those calls to run inside an existing JavaScript application.

Both modes support the same JavaScript functions. They differ in where the code runs and whether it shares state with your app.

| Mode | `bridge.hostMode` | Child process | RPC transport | Shared memory with app |
| --- | --- | --- | --- | --- |
| **Bootstrap** (default) | `false` | `{bridge.host}` runs `@forst/runtime` bootstrap | Unix socket (TCP on Windows) | No — isolated bridge child |
| **Host** | `true` | App shim (`bridge.binary` + `bridge.args`) | Unix socket (TCP on Windows) | **Yes** — RPC runs inside the app process |

Set `bridge.host` to `node` (default), `bun`, or `deno` (requires `FORST_DENO_HOST_ENABLED=1`).
Both modes use the same `@forst/runtime` RPC protocol. Only the interpreter and argv prefix differ.

### Bootstrap mode (default)

Use bootstrap mode unless your JavaScript depends on state held by an existing app process. Forst starts a dedicated bridge child and forwards its logs.

The process uses a local socket at `.forst/node-bootstrap.sock` by default. This is what `task example:bridge-interop-sync` and the other basic examples use.

Bootstrap always runs `@forst/runtime/dist/bootstrap.js`. Forst picks the executable from `bridge.host` (or `bridge.binary` when it names a Node, Bun, or Deno binary).

```text
# Node, compiled format (default)
node node_modules/@forst/runtime/dist/bootstrap.js

# Node, typescript format with tsx on argv instead of NODE_OPTIONS
node --import tsx/dist/loader.mjs node_modules/@forst/runtime/dist/bootstrap.js

# Bun with native TypeScript without tsx
bun node_modules/@forst/runtime/dist/bootstrap.js

# Deno with permission flags and bootstrap script
deno run --allow-read=… --allow-write=… --allow-env --allow-net=127.0.0.1 \
  node_modules/@forst/runtime/dist/bootstrap.js
```

### Host mode (shared memory)

Use host mode when the JavaScript call must see the same state as your running JavaScript app. Common examples include a Prisma client, global instrumentation, and modules already loaded by Remix or Vite.

Host mode runs Forst calls inside that app process. This preserves the module cache and global values.

The app may need time to finish setup before it can accept calls. Forst waits for an app ready signal before connecting.

### Default third party shims

Go auto injects a blocking `register.mjs` preload when `hostMode` is enabled (`hostAutoRegister`, default `true`). The flag is host specific and passed on the direct shim argv only, without `NODE_OPTIONS`, so worker processes do not each try to bind the host socket.

| Host | Register preload on argv |
| --- | --- |
| Node | `--import @forst/runtime/dist/host/register.mjs` |
| Bun | `--preload @forst/runtime/dist/host/register.mjs` |
| Deno | `--preload=@forst/runtime/dist/host/register.mjs` (with `deno run` permission flags) |

For shims that do not need a custom init hook, omit `hostAppReadyModule`. `register.mjs` signals readiness as soon as the host socket is listening. Only set `hostAppReadyModule` when you need to run setup code before RPC. It must be a small module without side effects and without your full server bundle.

```json
{
  "bridge": {
    "host": "node",
    "hostMode": true,
    "binary": "node_modules/.bin/remix-serve",
    "args": ["./build/server/index.js", "--port", "3000"],
    "hostSocket": ".forst/node.sock",
    "hostReadyTimeoutSeconds": 120
  }
}
```

The example above uses Node because remix-serve is a Node shim. Set `bridge.host` and `bridge.binary` to match your runtime (`bun`, `deno`, or another app entry).

### Custom server entry

After seeding shared state, call `signalForstAppReady()`.

```typescript
import { signalForstAppReady } from "@forst/runtime/host";

globalThis.__forstTest = { n: 1 };
await signalForstAppReady();
```

The auto injected `register.mjs` script runs `startForstNodeHost({ deferAppReady: true })` before your entry module.

### Manual preload

You can opt out with `hostAutoRegister: false` and pass a manual preload.

```text
# Node
node --import @forst/runtime/host/register.mjs ./your-server.mjs

# Bun
bun --preload @forst/runtime/host/register.mjs ./your-server.mjs
```

| Field | Purpose |
| --- | --- |
| `bridge.hostMode` | When `true`, Go spawns `bridge.binary` with `bridge.args` instead of bootstrap |
| `bridge.args` | Required when `hostMode` is true — argv passed to the app shim |
| `bridge.hostAutoRegister` | Prepend host specific register preload on the direct shim argv (default `true` when `hostMode`) |
| `bridge.hostAppReadyModule` | Optional module loaded before `signalForstAppReady()` when auto register needs deferred readiness |
| `bridge.hostSocket` | Relative path under boundary root for the Unix socket (default `.forst/node.sock`) |
| `bridge.hostReadyTimeoutSeconds` | Max wait for `phase: "app"` ready marker (default `120`) |

### Socket RPC environment variables

Most users do not need these variables. Forst sets them when it starts or joins the bridge process. Use this table when debugging custom startup behavior.

Bootstrap uses `@forst/runtime/dist/bootstrap.js`. Host mode uses `@forst/runtime/host` and `host/register.mjs`.

| Variable | Set by | Purpose |
| --- | --- | --- |
| `FORST_BRIDGE_HOST` | Go (`"1"`, host only) | Enables in-process host RPC. When unset, `startForstNodeHost()` does nothing. Bootstrap mode does not set this. |
| `FORST_BRIDGE_HOST_LEADER` | Go (`"1"`, host only) | Marks the process Go spawned as the sole host leader. `startForstNodeHost()` requires this and `register.mjs` in `process.execArgv`. Child worker processes (Vite, Remix, etc.) may inherit `FORST_BRIDGE_HOST` but skip binding when they lack leader and preload flags. |
| `FORST_BRIDGE_SOCKET` | Go | Absolute path to the Unix socket (TCP URL on Windows) where the bridge listens for Go RPC. Bootstrap defaults to `{boundaryRoot}/.forst/node-bootstrap.sock`. Host defaults to `{boundaryRoot}/{bridge.hostSocket}` (default `.forst/node.sock`). If set in the parent environment before spawn, planning uses it. |
| `FORST_BRIDGE_HOST_READY` | Go | Absolute path to a JSON readiness file (typically `{socket}.ready`). The bridge writes `{"pid", "socket", "phase"}` after listening. Go polls until `phase` is `"app"` before dialing. Bootstrap signals `phase: "app"` immediately after listening. Host may defer until Remix, Vite, or your entry calls `signalForstAppReady()`. |
| `FORST_BRIDGE_APP_READY_MODULE` | Go (optional, host only) | When `bridge.hostAppReadyModule` is set in ftconfig, path to a small module `register.mjs` loads before signaling app readiness. |
| `FORST_BRIDGE_ATTACH_ONLY` | `forst dev` parent (`"1"`) | Set on `go run` children during watch reload. Bridgert reattaches to the running process without spawning a new host. Unset for one-shot `forst run`. |
| `FORCE_COLOR` | Go (optional, host only) | Set to `"1"` when the Forst parent stdout is a TTY and `NO_COLOR` is unset, so piped output keeps ANSI colors. |

### Dev reload host ownership

During development, Forst keeps the bridge host running while it rebuilds and restarts the Go side. This avoids restarting Vite, Remix, or another JavaScript app after every `.ft` change.

With `bridge.hostMode` and `forst dev`:

- `forst dev` (parent) spawns and owns the app host before starting the compiled `go run` child.
- Each reload `go run` child inherits `FORST_BRIDGE_ATTACH_ONLY=1` and dials the existing host socket. It never spawns a second host.
- Reload stop sends process group signals to `go run`. The host process runs separately from that child, so Vite stays running on every `.ft` save.
- `forst dev` exit always stops the host process.

One-shot `forst run` with `hostMode` is unchanged. The compiled binary spawns the host on first `GetClient()` when attach-only is unset.

In production with `forst build -o <dir>`, `server.embedded`, and `bridge.hostMode`, the linked program binary acts as the parent. It runs the embedded invoke server and spawns the bridge host as a child.

```text
bin/main
  ├─ embedded invoke
  └─ bridge host child (bridge.binary + bridge.args)
       └─ legacy JS via bridgert socket RPC
```

Set `FORST_SKIP_NODE_HOST=1` on the same binary when the JavaScript host runs separately and the binary should not spawn it.

Typical spawn layout for Node host in typescript format.

```text
node --import tsx/dist/loader.mjs --import @forst/runtime/dist/host/register.mjs node_modules/.bin/vite dev
```

With `format: compiled` (default), omit the tsx `--import`. Bun and Deno use `--preload` or `deno run` permission flags instead of Node `--import`. See the host register table above.

Go dials `FORST_BRIDGE_SOCKET` after `FORST_BRIDGE_HOST_READY` reports `phase: "app"`.

<Warning>
  Use host mode for app shims (remix-serve, Vite, custom servers) when the legacy app must share module cache and globals with Forst RPC. Both bootstrap and host use socket RPC so app logs stay clean.
</Warning>

#### Shared memory semantics

RPC dispatcher, `require` or `import` cache, and `globalThis` state in the app process stay visible to TypeScript modules loaded via RPC. An isolated bootstrap child reloads modules in a separate process.

#### Failure modes

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `host ready timeout` | Bridge process never wrote `phase: "app"` to the ready marker | Bootstrap: check `@forst/runtime` build and `FORST_BRIDGE_SOCKET`. Host: omit `hostAppReadyModule` or call `signalForstAppReady()` after init. |
| `ErrNodeRuntimeDied` during RPC | App process crashed or socket closed | Check child stderr logs or app crash output. |
| Second Go client | Host rejects duplicate connections | Keep a single client connection per host process. |
| `EADDRINUSE` on `.forst/node.sock` | Stale host or duplicate leader | Use default `hostAutoRegister` (argv preload). Ensure only one `forst run` owns the socket. |
| Multiple `host_listening` lines | Workers attempted host bind | Use argv preload so workers log `host_skip_non_leader` when inheriting host environment variables. |

Compile time indexing always uses bootstrap mode. The indexer runs `forst-runtime-index` CLI and never runs the app shim.

## Security model

Forst only allows calls that were visible when you built the program. JavaScript cannot ask the bridge to load an arbitrary file or call an unknown export.

The sections below explain how that restriction is enforced.

### Allowed calls

During the build, Forst records each module and export your program can call. That list is stored in the generated Go binary.

Internally, the list uses the `forst-node-manifest-v1` format. Each entry records the module, export name, and function kind. One entry might describe `legacy/payment.ts`, `create`, and `function`.

The Go bridge only emits calls for entries it compiled. The bridge runtime rechecks every RPC against the same manifest before loading modules or calling exports.

### How bootstrap starts the bridge child

Bootstrap mode starts a small Forst owned script. The bridge script runs as the process entry. Your modules load only when an allowed call needs them.

Typical spawn commands by host in compiled format.

```text
node node_modules/@forst/runtime/dist/bootstrap.js
bun node_modules/@forst/runtime/dist/bootstrap.js
deno run --allow-read=… node_modules/@forst/runtime/dist/bootstrap.js
```

With `bridge.legacyModules.format: "typescript"`, Node prepends `--import tsx/dist/loader.mjs` on argv. Bun and Deno load TypeScript natively without tsx.

User TypeScript loads only through controlled `import()` calls inside the bootstrap, triggered by an allowed RPC. Bootstrap RPC uses a local socket (`FORST_BRIDGE_SOCKET` and `FORST_BRIDGE_HOST_READY`, default `.forst/node-bootstrap.sock`). Runtime logs go to stderr and child stdout and stderr output is forwarded to the Forst parent.

In host mode, Go spawns your app shim (`bridge.binary` and `bridge.args`) and connects over a local socket. The app imports `@forst/runtime/host` so RPC runs in process. Manifest and path rules stay the same.

Bootstrap resolution order.

1. `FORST_BRIDGE_BOOTSTRAP` environment variable (absolute path)
2. `node_modules/@forst/runtime/dist/bootstrap.js` under the boundary root
3. Checkout or vendor path when developing from the [forst-lang/forst](https://github.com/forst-lang/forst) repository: `packages/runtime/dist/bootstrap.js`

### Allowed runtime messages

The local connection accepts a fixed set of messages for calls, generators, and shutdown. Unknown messages are rejected before user code runs.

The connection starts with `forst.node/initialize`.

| Protocol ID | Transport |
| --- | --- |
| `forst-node-proto-v1` | Length prefixed protobuf frames. Method payloads are JSON inside `payload_json` or `ok_json`. |

Only documented methods are accepted (`forst.node/initialize`, `forst.node/call`, `forst.node/callAsync`, `forst.node/genOpen`, `forst.node/genNext`, `forst.node/genNextBatch`, `forst.node/genClose`, and `forst.node/shutdown`). Unknown methods or manifest entries return `forst.node/forbidden` (`-32001`) before any user code runs.

Path rules reject `..`, absolute paths, and modules outside `boundaryRoot`.

<Info>
  This boundary is for same machine and same trust zone calls. For cross service or remote clients, use the HTTP sidecar instead of widening the RPC surface.
</Info>

## Sync, async, and generators

Forst can call normal functions, async functions, and generators. The Forst call site stays synchronous. The JavaScript side waits for promises and pulls generator values when needed.

The build records what kind of export each function is.

| TS export | Indexed kind | Forst usage |
| --- | --- | --- |
| `export function` | `function` | Direct call with sync RPC |
| `export async function` | `asyncFunction` | Direct call that blocks until Promise settles |
| `export function*` | `generator` | `seq := mod.gen(...); ensure seq is Ok(); for _, x := range seq` |
| `export async function*` | `asyncGenerator` | Same as sync generator (`Seq[T]` at the Forst boundary) |

### Sync calls

Normal JavaScript functions look like ordinary calls in Forst. The result is wrapped in `Result(T, Error)` because the local bridge call can still fail.

Use `ensure … is Ok()` or `if … is Err()` before using the returned value.

Sync call from Forst.

```ft
import "./legacy/payment" js

func main() {
    result := payment.create(100.0, "USD")
    ensure result is Ok()
    println(result.id)
}
```

### Async TypeScript from sync Forst

You can call an async TypeScript function from ordinary Forst code. The bridge waits for the promise and sends its value back. You do not add `async` or `await` to the Forst function.

The result is still `Result(T, Error)`. Here, `T` is the value produced by the promise.

The call site looks the same.

```ft
import "./legacy/payment" js

func main() {
    result := payment.create(100.0, "USD")
    ensure result is Ok()
    println(result.id)

    echo := payment.concurrentEcho(7.0)
    ensure echo is Ok()
    println(echo.echo)
}
```

### Outer errors and inner values

Two different things can go wrong. The bridge itself can fail, or the JavaScript function can return a business failure as part of its normal value. Keeping them separate helps you decide where to handle each one.

| Layer | What fails | Forst type |
| --- | --- | --- |
| Outer (compiler) | RPC timeout, manifest forbidden, TS throw, Promise rejection | `Error` on `Result(..., Error)` |
| Inner (indexer) | Business outcome inside the settled value | Indexed `returnType` (may be a union or Result shape from TypeScript) |

If a TypeScript `async function` resolves to a tagged union or Result like value, the indexer maps that as `T`. The outer call is `Result(T, Error)`.

### Use several modules and generators

One Forst function can call several JavaScript modules. It can also combine async functions with generators. The Forst code remains synchronous.

```ft
import "./legacy/payment" js
import "./legacy/events" js

func checkout(amount Float, currency String): String {
    result := payment.create(amount, currency)
    ensure result is Ok()
    return result.id
}

func drainEvents(userId String): Int {
    var count: Int = 0
    seq := events.subscribe(userId)
    ensure seq is Ok()
    for _, evt := range seq {
        events.dispatch(evt)
        count = count + 1
    }
    return count
}
```

### Generators and `Seq[T]`

JavaScript generators appear as `Seq[T]` in Forst. Check that the generator opened successfully, then use a normal `for range` loop to read its values.

Both sync and async JavaScript generators use the same `Seq[T]` shape. The bridge handles the difference while Forst pulls values as the loop needs them.

Pull values from a generator export.

```ft
import "./legacy/generators" js

func main() {
    seq := generators.syncNumbers(3.0)
    ensure seq is Ok()
    var sum: Float = 0.0
    for _, n := range seq {
        sum = sum + n
    }
    println(string(Int(sum)))
}
```

Generated Go uses `bridgert.OpenSeq` via companion wrappers. `for range` lowers to batched `NextBatch` pulls to cut RPC round trips.

## Generated runtime files

Forst only adds the JS bridge when your app uses it. A program with no reachable JS import stays a normal Go binary with no JavaScript requirement.

The compiler checks the whole program to make this decision. Internally, the result is tracked as `needsNodeRuntime`.

| Value | Generated app | Deployment |
| --- | --- | --- |
| `false` | No JS bridge or manifest | JavaScript runtime is not required |
| `true` | JS bridge and embedded allowlist | Bridge host + `@forst/runtime` required (tsx only when `format: typescript` on Node) |

When the bridge is needed, the compiler emits your normal Go output and a companion `*_forst_0_node_runtime.gen.go` file. The companion contains the allowed calls and the RPC wrappers. It imports [`forst/bridgert`](https://github.com/forst-lang/forst/tree/main/forst/bridgert), so your `go.mod` must resolve the `forst` Go module.

The requirement follows imports across packages. A direct JS import in `main.ft` is not required. Any reachable package can cause the final app to need JavaScript.

## How Forst learns TypeScript types

Forst reads your TypeScript exports during the build. This is how it checks function names, arguments, return values, and generator values before the app runs.

The `forst-runtime-index` tool performs this scan and returns an in memory `IndexV1` record. It does not write index files into your project. Forst uses that record for type checking and for the list of calls allowed at runtime.

A JavaScript runtime and `@forst/runtime` must be available during the build when your program contains a JS import.

## How TypeScript types map to Forst

Common TypeScript types have direct Forst equivalents. Forst applies these mappings when it checks a JavaScript call.

| Index kind | Forst type |
| --- | --- |
| `string` | `String` |
| `number` | `Float` |
| `boolean` | `Bool` |
| `void` | `Void` |
| `bytes` | `Bytes` (`[]byte` in Go) |
| `array` | `[]T` (element mapped recursively) |
| `object` (no fields) | `Object` |
| `object` (with fields) | shape assertion type |
| `union` | `A \| B \| …` when every member maps; otherwise `Object` |
| `unknown` | `Object` (escape hatch for unmapped TS types) |

Generated Go uses thin `forst_node_*` wrappers in the companion file. Those call `bridgert.CallSync` or `bridgert.CallAsync` (or `CallSyncArgs` / `CallSyncArgs` when call arguments are compile time literals). `for range` over `Seq[T]` lowers to batched `NextBatch` pulls on the wrapper iterator type.

Union members that cannot be mapped, or unions with no members, widen to `Object`. The compiler emits a warning when this happens. Narrow the TypeScript export or add explicit fields.

## Troubleshooting

Start with the error text and find the matching row. Most problems come from a missing runtime package, a module that was not imported with the **`js`** marker, or a bridge process that did not become ready.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `cannot import TypeScript module without import "./path" js` | `.ts` exists but import is not opted in | Use `import "./path" js` or `import alias "./path" js` |
| `JS import local name "…" is a Forst keyword` (or Go keyword / not a valid identifier) | Default local name is reserved or invalid | Add an alias, e.g. `import typePkg "./legacy/type.ts" js` |
| `node runtime: bootstrap not found` | `@forst/runtime` not installed or not built | Run `npm install @forst/runtime`. Set `FORST_BRIDGE_BOOTSTRAP` to an absolute bootstrap path for custom layouts. |
| `node runtime: tsx loader not found` | `tsx` missing while `format: typescript` on Node | Install `tsx` at the project root or switch to `format: compiled`. |
| `host ready timeout` | Bootstrap or host ready marker never reached `phase: "app"` | Bootstrap: verify bootstrap spawn and socket environment. Host: omit `hostAppReadyModule` for third party shims, or call `signalForstAppReady()` in your entry. |
| `bridge.hostMode requires non-empty bridge.args` | `hostMode: true` without shim argv | Set `bridge.args` to your app entry (e.g. `["./build/server/index.js"]`). |
| Node spawn fails or `executable file not found` | `node` not on `PATH` | Install Node ≥ 20. Ensure `PATH` in production matches dev. |
| `forst.node/forbidden` or `ErrForbidden` at runtime | Call not in embedded manifest | Rebuild after adding exports. Ensure the call site was compiled with opt-in. |
| Works locally, fails in CI image | Binary needs JavaScript runtime but image lacks it | Install Node or Bun and runtime dependencies in the image, or remove opted in TS imports so the binary does not need a JS runtime. |

Enable debug logging on the Forst side to trace spawn, RPC, and forwarded stderr.

```bash
FORST_LOG_LEVEL=debug npx forst run -root ./my-service ./main.ft
```

For OpenTelemetry span export from the bootstrap child, set `OTEL_EXPORTER_OTLP_ENDPOINT` (or `FORST_BRIDGE_OTEL=1` for console export) and install the optional `@forst/runtime` OTEL peers. See [`@forst/runtime` README](https://github.com/forst-lang/forst/tree/main/packages/runtime#opentelemetry-optional).

## Migration from `importPolicy: "implicit"`

This section only applies to projects that used an early version of Node interop. Current projects should keep the default explicit import policy.

Older projects may have:

```json
{
  "bridge": {
    "importPolicy": "implicit"
  }
}
```

Under `implicit`, relative imports can resolve `.ts` without a directive. That widens the compile graph and sets `needsNodeRuntime` whenever any reachable `.ts` module exists, even if authors did not intend Node at deploy time.

Recommended migration steps.

1. Set `"importPolicy": "explicit"` in `ftconfig.json`.
2. Add `import "./…" js` (or `import alias "./…" js`) to every TypeScript import.
3. Rebuild and confirm which binaries report Node required.
4. Remove `implicit` once all imports use explicit.

Explicit opt-in makes intent visible in code review and keeps allowlists minimal.

## Caveats

JavaScript interop is experimental. Pin the `@forst/runtime` version and test your main call paths before using it in production.

### `forst/bridgert` dependency

Apps that call JavaScript include a small Go bridge. Your `go.mod` must resolve the `forst` Go module so generated code can import [`forst/bridgert`](https://github.com/forst-lang/forst/tree/main/forst/bridgert).

### Whole program JavaScript requirement

A JavaScript runtime is required when any reachable Forst package calls JavaScript. The JS import line does not need to appear in `main.ft`. It may come from a package that `main` uses.

### Unknown calls are blocked

The bridge only accepts calls recorded during the build. Unknown modules, exports, and message types are rejected before user code runs.

### Bootstrap vs host mode

Bootstrap mode runs JavaScript in a separate process. Host mode runs it inside your app process so both sides see the same module cache and global values.

### Type mapping limits

Some TypeScript types have no precise Forst equivalent. When a union cannot be mapped, Forst uses `Object` and shows a warning. Narrow the TypeScript return type or use an object with explicit fields when you need stronger checking.
