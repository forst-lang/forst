---
title: "Call JavaScript from Forst"
description: "Reuse existing TypeScript and JavaScript code while moving backend work to Forst."
---

Forst can call functions from your existing TypeScript and JavaScript modules.
This lets you move backend code to Forst one part at a time. Working Node code
can stay in place while new code compiles to Go.

To call Forst from Node instead, see [Call Forst from Node](/interop/node/call-forst). For shared types only, see [Generate client types](/interop/node/generate-types).

## Your first call

Start with an ordinary TypeScript module at `legacy/payment.ts`:

```typescript
export function create(amount: number, currency: string): { id: string } {
  return { id: "pay_1" };
}
```

Import that module in Forst and call the export:

```ft
import "./legacy/payment" node

func main() {
  result := payment.create(100.0, "USD")
  ensure result is Ok()
  println(result.id)
}
```

The postfix **`node`** marker tells Forst that this path points to a Node module. The compiler
checks the function name, arguments, and return value. The call returns a
`Result`, so `ensure result is Ok()` handles failures before you use the value.

At runtime, the compiled app starts a local Node process when it first needs
one. Calls stay on the same machine. If your program does not use a Node import (`import "./path" node`),
the compiled binary does not need Node.

## Set up Node interop

Install Forst first. See [Installation](/installation) for npm and native
options.

Install the runtime package:

```bash
npm install @forst/node-runtime
```

Node interop uses the same `ftconfig.json` boundary as `forst dev` and
`forst generate`. Include your TypeScript files and enable the runtime:

```json
{
  "files": {
    "include": ["**/*.ft", "**/*.ts", "**/*.tsx"],
    "exclude": ["**/node_modules/**", "**/.git/**"]
  },
  "node": {
    "enabled": true,
    "importPolicy": "explicit",
    "runtimeEnabled": true
  }
}
```

Forst only loads modules opted in with the postfix **`node`** marker. Plain imports never start the
Node bridge.

## Import a module

Use the file name as the local name, or choose an alias:

| Form | Example | Local name |
| --- | --- | --- |
| File name | `import "./legacy/payment" node` | `payment` |
| Alias | `import checkout "./legacy/api/checkout" node` | `checkout` |

You can also place Node imports inside a grouped import:

```ft
import (
  "strconv"
  "./legacy/payment" node
  checkout "./legacy/api/checkout" node
)

func main() {
  result := payment.create(100.0, "USD")
  ensure result is Ok()
  println(result.id)
}
```

Each import exposes the module namespace. For example, `payment.create` calls
the `create` export. Your TypeScript files need no Forst annotations.

### When the file or package name is reserved

If the default local name is a Forst or Go keyword, or not a valid identifier,
Forst reports an error at the import and suggests an alias:

```ft
import typePkg "./legacy/type.ts" node
import effectLib "@effect/platform" node
import my_package "@scope/my-package" node
```

Common cases:

| Path or package | Problem | Fix |
| --- | --- | --- |
| `./legacy/type.ts` | `type` is a keyword | `import typePkg "./legacy/type.ts" node` |
| `"map"` (npm) | `map` is a keyword | `import mapPkg "map" node` |
| `@scope/my-package` | hyphens are invalid in identifiers | `import my_package "@scope/my-package" node` |

Scoped npm packages such as `@effect/platform` default to the last path segment
(`platform`) when that name is valid.

## Build and run

Use `build` when you want Go output for deployment. Use `run` when you want to
compile and start the program in one step.

Enable embedded invoke in `ftconfig.json` before a production build:

```json
{
  "server": { "embedded": true }
}
```

```bash
npx forst build -root ./my-service -o .forst/build -- ./cmd/api/main.ft
npx forst run -root ./my-service ./cmd/api/main.ft
```

Production exec (read `binary` from `manifest.json`, for example `bin/main`):

```bash
FORST_ROOT=/app /app/.forst/build/bin/main
```

Your deployed app needs a JavaScript bridge host and `@forst/node-runtime` when any reachable
Forst package uses a Node import. Production builds default to **compiled** legacy modules
under `.forst/js/` (esbuild bundles at compile time). In that mode you do **not** need `tsx` at
runtime. Set `javascript.legacyModules.format` to `"typescript"` only when you intentionally load
`.ts`/`.tsx` source files in production (Node host only).

Repository examples:

| Example | Phase | Command |
| --- | --- | --- |
| Compile-time fixture | 1 | `task example:node-interop` |
| Sync RPC | 2 | `task example:node-interop-sync` |
| Async RPC (TS `async function`) | 3 | `task example:node-interop-promises` |
| Generators | 4 | `task example:node-interop-generators` |
| Multi-module async + generators (blocking) | 3–4 | `task example:node-interop-async` |
| Host mode (shared memory, socket RPC) | 5 | `task example:node-interop-host` |

## Choose how Node runs

Configure the bridge with `javascript.host` (`node`, `bun`, or `deno` when enabled) and
`javascript.legacyModules.format` (`compiled` or `typescript`). The deprecated `node.loader`
field maps to format for older configs (`tsx` → typescript on Node only, `none` → compiled).
The deprecated `legacyModules.artifact` key and values `source` / `precompiled` are still accepted.

| Host | Module format | Runtime needs |
| --- | --- | --- |
| `node` (default) | `compiled` (default) | Node + `@forst/node-runtime` + `.forst/js/` beside the binary |
| `node` | `typescript` | Node + `tsx` + `@forst/node-runtime` |
| `bun` | either | Bun + `@forst/node-runtime` (no `tsx`) |
| `deno` | either | Deno + `@forst/node-runtime` when `FORST_DENO_HOST_ENABLED=1` |

Example production config:

```json
{
  "javascript": {
    "host": "node",
    "legacyModules": {
      "format": "compiled",
      "precompile": { "outDir": ".forst/js" }
    }
  },
  "node": { "binary": "node" }
}
```

When you use `forst build -o`, copy the `.forst/js` tree next to the output binary (Forst does
this automatically). Set `FORST_ROOT` to the deployment boundary so module IDs resolve.

**Bridge-host E2E (contributors):** CI runs Bun and Deno bootstrap tests via `task test:bridge-host-e2e`
(from repo root). Locally, install Bun (see root `package.json` `packageManager`) and Deno matching
[`.deno-version`](https://github.com/forst-lang/forst/blob/main/.deno-version) on your `PATH`, build
`packages/node-runtime`, then run that task. Without both hosts, the Go tests skip instead of fail.

Most projects should use bootstrap mode. It starts a small bridge process for Forst
calls. Host mode is for apps that need those calls to run inside an existing
JavaScript application.

Both modes support the same JavaScript functions. They differ in where the code
runs and whether it shares state with your app.

| Mode | `node.hostMode` | Child process | RPC transport | Shared memory with app |
| --- | --- | --- | --- | --- |
| **Bootstrap** (default) | `false` | `node` + Forst `bootstrap.js` | Unix socket (TCP on Windows) | No — isolated Node child |
| **Host** | `true` | App shim (`node.binary` + `node.args`) | Unix socket (TCP on Windows) | **Yes** — RPC runs inside the app process |

### Bootstrap mode (default)

Use bootstrap mode unless your JavaScript depends on state held by an existing
Node app. Forst starts a dedicated Node process and forwards its logs.

The process uses a local socket at `.forst/node-bootstrap.sock` by default. This
is what `task example:node-interop-sync` and the other basic examples use.

Bootstrap process layout (Node, compiled format — default):

```text
node node_modules/@forst/node-runtime/dist/bootstrap.js
```

With `format: "typescript"` on Node, Forst prepends `--import tsx/dist/loader.mjs` on argv (never via
`NODE_OPTIONS`). Bun uses `--preload` for host register instead of Node `--import`.

### Host mode (shared memory)

Use host mode when the JavaScript call must see the same state as your running
Node app. Common examples include a Prisma client, global instrumentation, and
modules already loaded by Remix or Vite.

Host mode runs Forst calls inside that app process. This preserves the module
cache and global values.

The app may need time to finish setup before it can accept calls. Forst waits
for an app ready signal before connecting.

**Default (third-party shims like remix-serve):** Go auto-injects a blocking `register.mjs` preload when `hostMode` is enabled (`hostAutoRegister`, default `true`). The preload is passed as a **`node --import`** flag on the **direct** shim spawn only — not via `NODE_OPTIONS` — so Vite/Remix worker processes do not each try to bind the host socket. For shims that do not need a custom init hook, omit `hostAppReadyModule` — `register.mjs` signals readiness as soon as the host socket is listening. Only set `hostAppReadyModule` when you need to run setup code **before** RPC (must be a tiny, side-effect-free module — never your full server bundle):

```json
{
  "node": {
    "hostMode": true,
    "binary": "node_modules/.bin/remix-serve",
    "args": ["./build/server/index.js", "--port", "3000"],
    "hostSocket": ".forst/node.sock",
    "hostReadyTimeoutSeconds": 120
  }
}
```

**Custom server entry:** after seeding shared state, call `signalForstAppReady()`:

```typescript
import { signalForstAppReady } from "@forst/node-runtime/host";

globalThis.__forstTest = { n: 1 };
await signalForstAppReady();
```

(`startForstNodeHost({ deferAppReady: true })` runs via auto-injected `register.mjs` before your entry module.)

**Manual preload** (advanced; opt out with `hostAutoRegister: false`):

```text
node --import @forst/node-runtime/host/register.mjs ./your-server.mjs
```

| Field | Purpose |
| --- | --- |
| `node.hostMode` | When `true`, Go spawns `node.binary` with `node.args` instead of bootstrap |
| `node.args` | **Required** when `hostMode` is true — argv passed to the app shim |
| `node.hostAutoRegister` | Prepend `--import register.mjs` on the direct shim argv (default `true` when `hostMode`) |
| `node.hostAppReadyModule` | Optional module loaded before `signalForstAppReady()` when auto-register needs deferred readiness (not your server entry) |
| `node.hostSocket` | Relative path under boundary root for the Unix socket (default `.forst/node.sock`) |
| `node.hostReadyTimeoutSeconds` | Max wait for `phase: "app"` ready marker (default `120`) |

### Socket RPC environment variables

Most users do not need these variables. Forst sets them when it starts or joins
the Node process. Use this table when debugging custom startup behavior.

Bootstrap uses `@forst/node-runtime/dist/bootstrap.js`. Host mode uses
`@forst/node-runtime/host` and `host/register.mjs`.

| Variable | Set by | Purpose |
| --- | --- | --- |
| `FORST_NODE_HOST` | Go (`"1"`, host only) | Enables in-process host RPC. When unset, `startForstNodeHost()` no-ops. **Bootstrap mode does not set this.** |
| `FORST_NODE_HOST_LEADER` | Go (`"1"`, host only) | Marks the process Go spawned as the **sole** host leader. `startForstNodeHost()` requires this **and** `register.mjs` in `process.execArgv`. Child Node processes (Vite workers, etc.) may inherit `FORST_NODE_HOST` but must not bind the socket — they lack leader + preload and skip with `host_skip_non_leader`. |
| `FORST_NODE_SOCKET` | Go | Absolute path to the Unix socket (TCP URL on Windows) where Node listens for Go RPC. **Bootstrap** defaults to `{boundaryRoot}/.forst/node-bootstrap.sock`; **host** defaults to `{boundaryRoot}/{node.hostSocket}` (default `.forst/node.sock`). If set in the **parent** environment before spawn, `ResolveHostSocketPath` / `ResolveBootstrapSocketPath` use it for planning. |
| `FORST_NODE_HOST_READY` | Go | Absolute path to a JSON readiness file (typically `{socket}.ready`). Node writes `{"pid", "socket", "phase"}` after listen; Go polls until `phase` is `"app"` before dialing. **Bootstrap** signals `phase: "app"` immediately after listen. **Host** may defer until Remix/Vite or your entry calls `signalForstAppReady()` when `hostAppReadyModule` is set. |
| `FORST_NODE_APP_READY_MODULE` | Go (optional, host only) | When `node.hostAppReadyModule` is set in ftconfig, path to a small module `register.mjs` loads before signaling app readiness. |
| `FORST_NODE_ATTACH_ONLY` | `forst dev` parent (`"1"`) | Set on **`go run` children** during watch reload. Nodert **reattaches only** — it does not spawn a new host. Unset for one-shot `forst run`. |
| `FORCE_COLOR` | Go (optional, host only) | Set to `"1"` when the Forst parent stdout is a TTY and `NO_COLOR` is unset, so piped Vite/Remix output keeps ANSI colors. |

### Dev reload host ownership

During development, Forst keeps the Node host running while it rebuilds and
restarts the Go side. This avoids restarting Vite, Remix, or another Node app
after every `.ft` change.

With `node.hostMode` and `forst dev`:

- **`forst dev` (parent)** spawns and owns the Node/Vite host before starting the compiled `go run` child.
- Each reload **`go run` child** inherits `FORST_NODE_ATTACH_ONLY=1` and dials the existing host socket — it never spawns a second host.
- Reload stop uses **process-group SIGTERM/SIGKILL on `go run` only**; the host is not a descendant of that child, so Vite does not cold-start on every `.ft` save.
- **`forst dev` exit always stops the host** (whether the parent spawned it or reattached to an existing marker).

One-shot `forst run` with `hostMode` is unchanged: the compiled binary may spawn the host on first `GetClient()` when attach-only is unset.

**Production (`forst build -o <dir>`)** with `server.embedded` + `node.hostMode`: one linked program binary is the parent. It runs embedded invoke and spawns the Node host as a child (same process tree as `forst run`, without `go` at runtime):

```text
bin/main
  ├─ embedded invoke
  └─ Node host child (node.binary + node.args)
       └─ legacy JS via nodert socket RPC
```

Set `FORST_SKIP_NODE_HOST=1` on the same binary when Node runs separately and the binary should not spawn the Node host.

Typical spawn layout (Node host, typescript format):

```text
node --import tsx/dist/loader.mjs --import @forst/node-runtime/dist/host/register.mjs node_modules/.bin/vite dev
```

With `format: compiled` (default), omit the tsx `--import`.

Go dials `FORST_NODE_SOCKET` after `FORST_NODE_HOST_READY` reports `phase: "app"`.

<Warning>
  **Use host mode for app shims** (remix-serve, Vite, custom servers) when the legacy app must share module cache and globals with Forst RPC. Both bootstrap and host use **socket RPC** so app stdout/stderr stay free for normal logging.
</Warning>

**Shared memory semantics:** RPC dispatcher, `require`/`import` cache, and `globalThis` state in the app process are visible to legacy TypeScript modules loaded via RPC. A separate bootstrap child would reload modules in an isolated process.

**Failure modes:**

| Symptom | Likely cause |
| --- | --- |
| `host ready timeout` | Node never wrote `phase: "app"` to the ready marker (bootstrap crash/hang, or host app readiness not signaled) | Bootstrap: check `@forst/node-runtime` build and `FORST_NODE_SOCKET`; host: omit `hostAppReadyModule` or call `signalForstAppReady()` after init |
| `ErrNodeRuntimeDied` during RPC | App process crashed; socket closed |
| Second Go client | Host rejects duplicate connections (single client invariant) |
| `EADDRINUSE` on `.forst/node.sock` | Stale host or duplicate leader (often from putting `register.mjs` in `NODE_OPTIONS`) | Use default `hostAutoRegister` (argv preload); ensure only one `forst run` owns the socket |
| Multiple `host_listening` lines | Vite/Remix workers attempted host bind | Fixed when register is argv-only; workers should log `host_skip_non_leader` if they inherit host env |

Compile-time **indexing always uses bootstrap mode** — the indexer runs `forst-node-index` CLI, never the app shim.

## Security model

Forst only allows calls that were visible when you built the program. JavaScript
cannot ask the bridge to load an arbitrary file or call an unknown export.

The sections below explain how that restriction is enforced.

### Allowed calls

During the build, Forst records each module and export your program can call.
That list is stored in the generated Go binary.

Internally, the list uses the `forst-node-manifest-v1` format. Each entry records
the module, export name, and function kind. One entry might describe
`legacy/payment.ts`, `create`, and `function`.

The Go bridge only emits calls for entries it compiled. The Node bootstrap **re-checks** every RPC against the same manifest before loading modules or calling exports.

### How bootstrap starts Node

Bootstrap mode starts a small Forst owned script. It does not run one of your
TypeScript files as the process entry. Your modules load only when an allowed
call needs them.

Typical spawn command (Node, compiled — default):

```text
node node_modules/@forst/node-runtime/dist/bootstrap.js
```

With `javascript.legacyModules.format: "typescript"`, Forst prepends `--import tsx/dist/loader.mjs` on argv.

User TypeScript loads only via controlled `import()` inside the bootstrap, triggered by an allowed RPC. Bootstrap RPC uses a local socket (`FORST_NODE_SOCKET` / `FORST_NODE_HOST_READY`, default `.forst/node-bootstrap.sock`); runtime logs go to stderr and child stdout/stderr are forwarded to the Forst parent.

In **host mode**, Go spawns your app shim (`node.binary` + `node.args`) and connects via a local socket. The app must import `@forst/node-runtime/host` so RPC runs in-process. Manifest and path rules are unchanged.

Bootstrap resolution order:

1. `FORST_NODE_BOOTSTRAP` environment variable (absolute path)
2. `node_modules/@forst/node-runtime/dist/bootstrap.js` under the boundary root
3. Checkout or vendor path when developing from the [forst-lang/forst](https://github.com/forst-lang/forst) repository: `packages/node-runtime/dist/bootstrap.js`

### Allowed runtime messages

The local connection accepts a fixed set of messages for calls, generators, and
shutdown. Unknown messages are rejected before user code runs.

The connection starts with `forst.node/initialize`:

| Protocol id | Transport |
| --- | --- |
| `forst-node-proto-v1` | Length-prefixed protobuf **frames**; method payloads are JSON inside `payload_json` / `ok_json` |

Only documented methods are accepted (`forst.node/initialize`, `forst.node/call`, `forst.node/callAsync`, `forst.node/genOpen`, `forst.node/genNext`, `forst.node/genNextBatch`, `forst.node/genClose`, `forst.node/shutdown`, …). Unknown methods or manifest entries return **`forst.node/forbidden`** (`-32001`) before any user code runs.

Path rules reject `..`, absolute paths, and modules outside the **`boundaryRoot`**.

<Info>
  This boundary is for **same-machine, same-trust-zone** calls. For cross-service or remote clients, use the HTTP sidecar instead of widening the Node RPC surface.
</Info>

## Sync, async, and generators

Forst can call normal functions, async functions, and generators. The Forst call
site stays synchronous. The Node side waits for promises and pulls generator
values when needed.

The build records what kind of export each function is:

| TS export | Indexed kind | Forst usage |
| --- | --- | --- |
| `export function` | `function` | Direct call — sync RPC |
| `export async function` | `asyncFunction` | Direct call — blocks until Promise settles |
| `export function*` | `generator` | `seq := mod.gen(...); ensure seq is Ok(); for _, x := range seq` |
| `export async function*` | `asyncGenerator` | Same as sync generator — `Seq[T]` at the Forst boundary |

### Sync calls

Normal JavaScript functions look like ordinary calls in Forst. The result is
wrapped in `Result(T, Error)` because the local Node call can still fail.

Use `ensure … is Ok()` or `if … is Err()` before using the returned value.

Sync call from Forst:

```ft
import "./legacy/payment" node

func main() {
    result := payment.create(100.0, "USD")
    ensure result is Ok()
    println(result.id)
}
```

### Async TypeScript from sync Forst

You can call an async TypeScript function from ordinary Forst code. Node waits
for the promise and sends its value back. You do not add `async` or `await` to
the Forst function.

The result is still `Result(T, Error)`. Here, `T` is the value produced by the
promise.

The call site looks the same:

```ft
import "./legacy/payment" node

func main() {
    result := payment.create(100.0, "USD")
    ensure result is Ok()
    println(result.id)

    echo := payment.concurrentEcho(7.0)
    ensure echo is Ok()
    println(echo.echo)
}
```

### Two layers of failure

Two different things can go wrong. The bridge itself can fail, or the
JavaScript function can return a business failure as part of its normal value.
Keeping them separate helps you decide where to handle each one.

| Layer | What fails | Forst type |
| --- | --- | --- |
| **Outer** (compiler) | RPC timeout, manifest forbidden, TS throw / Promise rejection | `Error` on `Result(..., Error)` |
| **Inner** (indexer) | Business outcome inside the settled value | Indexed `returnType` — may be a union or (future) `Result` shape from TypeScript |

If a TypeScript `async function` resolves to a tagged union or Result-like value, the indexer maps that as **`T`**; the outer call is **`Result(T, Error)`**.

### Use several modules and generators

One Forst function can call several JavaScript modules. It can also combine
async functions with generators. The Forst code remains synchronous.

```ft
import "./legacy/payment" node
import "./legacy/events" node

func checkout(amount Float, currency String): String {
    result := payment.create(amount, currency)
    ensure result is Ok()
    return result.id
}

func drainEvents(userId String): Int {
    var count: Int = 0
    seq := events.subscribe(userId)
    ensure seq is Ok()
    for _, evt := range seq {
        events.dispatch(evt)
        count = count + 1
    }
    return count
}
```

### Generators and `Seq[T]`

JavaScript generators appear as `Seq[T]` in Forst. Check that the generator
opened successfully, then use a normal `for range` loop to read its values.

Both sync and async JavaScript generators use the same `Seq[T]` shape. Node
handles the difference while Forst pulls values as the loop needs them.

Pull values from a generator export:

```ft
import "./legacy/generators" node

func main() {
    seq := generators.syncNumbers(3.0)
    ensure seq is Ok()
    var sum: Float = 0.0
    for _, n := range seq {
        sum = sum + n
    }
    println(string(Int(sum)))
}
```

Generated Go uses **`nodert.OpenSeq`** via companion wrappers. **`for range`** lowers to batched **`NextBatch`** pulls to cut RPC round trips.

## Generated runtime files

Forst only adds the Node bridge when your app uses it. A program with no
reachable Node import stays a normal Go binary with no Node requirement.

The compiler checks the whole program to make this decision. Internally, the
result is tracked as `needsNodeRuntime`.

| Value | Generated app | Deployment |
| --- | --- | --- |
| `false` | No Node bridge or manifest | Node is not required |
| `true` | Node bridge and embedded allowlist | Bridge host + `@forst/node-runtime` required (`tsx` only when `format: typescript` on Node) |

When Node is needed, the compiler emits your normal Go output and a companion
`*_forst_0_node_runtime.gen.go` file. The companion contains the allowed calls and
the RPC wrappers. It imports
[`forst/nodert`](https://github.com/forst-lang/forst/tree/main/forst/nodert), so
your `go.mod` must resolve the `forst` Go module.

The requirement follows imports across packages. A direct Node import in
`main.ft` is not required. Any reachable package can cause the final app to need
Node.

## How Forst learns TypeScript types

Forst reads your TypeScript exports during the build. This is how it checks
function names, arguments, return values, and generator values before the app
runs.

The `forst-node-index` tool performs this scan and returns an in-memory `IndexV1`
record. It does not write index files into your project. Forst uses that record
for type checking and for the list of calls allowed at runtime.

Node and `@forst/node-runtime` must be available during the build when your
program contains a Node import.

## How TypeScript types map to Forst

Common TypeScript types have direct Forst equivalents. Forst applies these
mappings when it checks a JavaScript call.

| Index kind | Forst type |
| --- | --- |
| `string` | `String` |
| `number` | `Float` |
| `boolean` | `Bool` |
| `void` | `Void` |
| `bytes` | `Bytes` (`[]byte` in Go) |
| `array` | `[]T` (element mapped recursively) |
| `object` (no fields) | `Object` |
| `object` (with fields) | shape assertion type |
| `union` | `A \| B \| …` when every member maps; otherwise `Object` |
| `unknown` | `Object` (escape hatch for unmapped TS types) |

Generated Go uses thin **`forst_node_*`** wrappers in the companion file; those call **`nodert.CallSync`** / **`nodert.CallAsync`** (or **`CallSyncArgs`** / **`CallAsyncArgs`** when call arguments are compile-time literals). **`for range`** over **`Seq[T]`** lowers to batched **`NextBatch`** pulls on the wrapper iterator type.

Union members that cannot be mapped, or unions with no members, widen to **`Object`** — the compiler emits a **warning** when this happens; narrow the TypeScript export or add explicit fields.

## Troubleshooting

Start with the error text and find the matching row. Most problems come from a
missing runtime package, a module that was not imported with the **`node`** marker, or a
Node process that did not become ready.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `cannot import TypeScript module without import "./path" node or import alias "./path" node` | `.ts` exists but import is not opted in | Use `import "./path" node` or `import alias "./path" node` |
| `node import local name "…" is a Forst keyword` (or Go keyword / not a valid identifier) | Default local name is reserved or invalid | Add an alias, e.g. `import typePkg "./legacy/type.ts" node` (see suggested fix in the error) |
| `node runtime: bootstrap not found` | `@forst/node-runtime` not installed or not built | `npm install @forst/node-runtime`; set `FORST_NODE_BOOTSTRAP` to an absolute bootstrap path for custom layouts |
| `node runtime: tsx loader not found` | `tsx` missing while `format: typescript` on Node | Install `tsx` at the project root or switch to `format: compiled` |
| `host ready timeout` | Bootstrap or host: ready marker never reached `phase: "app"` | Bootstrap: verify Node bootstrap spawn and socket env; host: omit `hostAppReadyModule` for third-party shims, or call `signalForstAppReady()` in your entry |
| `node.hostMode requires non-empty node.args` | `hostMode: true` without shim argv | Set `node.args` to your app entry (e.g. `["./build/server/index.js"]`) |
| Node spawn fails / `executable file not found` | `node` not on `PATH` | Install Node ≥ 20; ensure `PATH` in production matches dev |
| `forst.node/forbidden` / `ErrForbidden` at runtime | Call not in embedded manifest | Rebuild after adding exports; ensure the call site was compiled with opt-in |
| Works locally, fails in CI image | Binary has `needsNodeRuntime` but image has no Node | Either install Node + runtime deps in the image, or remove opted-in TS imports so the binary does not need Node |

Enable debug logging on the Forst side to trace spawn, RPC, and forwarded Node stderr:

```bash
FORST_LOG_LEVEL=debug npx forst run -root ./my-service ./main.ft
```

For OpenTelemetry span export from the Node bootstrap child, set `OTEL_EXPORTER_OTLP_ENDPOINT` (or `FORST_NODE_OTEL=1` for console export) and install the optional `@forst/node-runtime` OTEL peers. See [`@forst/node-runtime` README](https://github.com/forst-lang/forst/tree/main/packages/node-runtime#opentelemetry-optional).

## Migration from `importPolicy: "implicit"`

This section only applies to projects that used an early version of Node
interop. Current projects should keep the default explicit import policy.

Older projects may have:

```json
{
  "node": {
    "importPolicy": "implicit"
  }
}
```

Under **`implicit`**, relative imports can resolve `.ts` **without** a directive. That widens the compile graph and sets **`needsNodeRuntime`** whenever any reachable `.ts` module exists — even if authors did not intend Node at deploy time.

**Recommended migration:**

1. Set **`"importPolicy": "explicit"`** in `ftconfig.json`.
2. Add **`import "./…" node`** (or **`import alias "./…" node`**) to every TypeScript import.
3. Rebuild and confirm which binaries report Node required vs not required.
4. Remove **`implicit`** once all imports are explicit.

Explicit opt-in makes intent visible in code review and keeps allowlists minimal.

## Caveats

Node runtime interop is experimental. Pin the `@forst/node-runtime` version and
test your main call paths before using it in production.

### `forst/nodert` dependency

Apps that call JavaScript include a small Go bridge. Your `go.mod` must resolve
the `forst` Go module so generated code can import
[`forst/nodert`](https://github.com/forst-lang/forst/tree/main/forst/nodert).

### Whole program Node requirement

Node is required when any reachable Forst package calls JavaScript. The
The Node import line does not need to appear in `main.ft`. It may come from a
package that `main` uses.

### Unknown calls are blocked

The bridge only accepts calls recorded during the build. Unknown modules,
exports, and message types are rejected before user code runs.

### Bootstrap vs host mode

Bootstrap mode runs JavaScript in a separate Node process. Host mode runs it
inside your app process so both sides see the same module cache and global
values.

### Type mapping limits

Some TypeScript types have no precise Forst equivalent. When a union cannot be
mapped, Forst uses `Object` and shows a warning. Narrow the TypeScript return
type or use an object with explicit fields when you need stronger checking.
