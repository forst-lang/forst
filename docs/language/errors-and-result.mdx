## Result types

Functions that can fail with typed errors return **`Result(Success, Failure)`**. The failure side is constrained to the **`Error`** family today.

<ErrorsOkIntMain />

**`Ok`** and **`Err`** serve as discriminants for **`is`** / **`ensure`**. They are not yet general value constructors for building **`Result`** values at every call site.

## Return inference and implicit returns

Forst infers a function's return type from:

- explicit **`return`** statements
- **`ensure`** (often producing **`Result(S, Error)`** when no return type is declared)
- the **last expression** in the function body when no return type is declared in the signature

When the last statement is an expression and the function has no declared return type, that expression's value becomes the function return. Generated Go emits an explicit **`return`** for it.

Here **`f`** also returns **`Result(Int, Error)`**; generated Go contains **`return g()`**.

### Trailing calls and Go imports

Go multi-return in **single-value** expression position (including a trailing call used as an implicit return) maps to **`Tuple(T₁…Tₙ)`**, not **`Result`**. To return **`Result(T, Error)`** from a Forst function, use the n-value bridge:

```forst
n, err := pkg.F()
ensure !err or err
return n
```

With no declared return type, a trailing Go multi-return call makes the function return a **`Tuple`**, not **`Result`**. To log for side effects only, use Forst **`println`** / **`print`**, or declare an explicit return type on a [Provider contract method](/language/providers).

## Result and Tuple (permanently disjoint)

**`Result(S, F)`** and **`Tuple(T₁…Tₙ)`** are **different types** with **no conversion either way**.

- **`Result`** is Forst-native: an exclusive success/failure sum built via **`return`** + **`ensure`** inside functions whose return type is **`Result(...)`**.
- **`Tuple`** is what Go FFI honestly returns when a multi-return call is bound in **single-value** context (`x := pkg.F()`).
- **`Ok()` / `Err()`** narrowing applies only to **`Result`**. Using them on a **`Tuple`** is a normal type error.
- Bridge FFI to **`Result`** with **`n, err := …; ensure !err or err; return n`** (see [Go interop](#go-interop)).

## Go interop

Go multi-return in **single-value** expression position maps to **`Tuple(T₁…Tₙ)`** uniformly at the FFI boundary—there is **no** auto-fold to **`Result`**. Use **`n, err := pkg.F(); ensure !err or err; return n`** inside a **`Result`-returning** Forst function to bridge FFI to **`Result`** ergonomics. **`v, err := pkg.F()`** (n-value context) behaves like Go. Generated Go uses idiomatic error returns.

## Compared to Go error structs

In Go you might write:

```go
type InsufficientStock struct {
	StockKeepingUnit string
	Requested        int
	Available        int
}

func (e InsufficientStock) Error() string { ... }
```

Forst's **`error Name { … }`** syntax makes the intent explicit: this is a **failure variant**, a dedicated type for a specific failure mode rather than a generic struct with an `Error()` method attached by convention.

## Caveats

**Nominal errors** and **`Result`** are **experimental**. Check the [roadmap](/resources/roadmap) before relying on edge cases in production.

### `Result` failure side

The failure type parameter is constrained to the **`Error`** family today. Arbitrary non-**`Error`** failure types are not supported yet.

### `Ok` and `Err` role

**`Ok`** and **`Err`** are discriminants for **`is`** and **`ensure`**. They are not general value constructors at every call site yet.

### Implicit return trap

When a function has no declared return type, a trailing Go **multi-return** call bound in single-value position types as **`Tuple`**, not **`Result`**. Declare an explicit return type, or use the **`n, err := …; ensure !err or err; return n`** bridge when you need **`Result`**. Use **`println`** for void side effects.

### Nominal errors incomplete

**`ensure`** only failure authoring, **`or`** LUB rules, and TypeScript **`_tag`** export are still maturing. Treat generated error payloads as evolving. See [Generate client types § Caveats](/interop/node/generate-types#caveats).

For **`ensure x is Ok()`** narrowing limits, see [Ensure and narrowing § Caveats](/language/ensure-and-narrowing#caveats).
