Use `ensure` when your program should continue only after a value passes a
check. A failed check returns an error or exits early. A successful check
refines the value's type, which Forst reuses on following lines until dependent
data changes.

This keeps validation beside the code that depends on it. Use `if x is ...`
when you want to choose a branch instead of returning early.

## Stop when a check fails

Write `ensure value is Condition()` to check a value. Add `else` when you want to
return a specific error. This `drive` function rejects a speed that is too
high, then updates a shared `position`.

<EnsureSpeed />

When the check fails, `drive` returns `TooFast`. `position` stays unchanged.
`position += speed` runs only after the speed passes.

<Note>
  See [Errors and Result](/language/errors-and-result) for how to define named
  errors such as `TooFast`.
</Note>

Forst provides built in conditions such as `LessThan`, `Min`, `Present`, and `Ok`.
The `is` operator runs the check and refines the value's type after success.
See the [full list of constraints](/language/shapes-and-constraints#reference).

## Choose the failure path with `else`

Use `else` after a check when failure should return a specific error.

```ft
ensure speed is LessThan(100) else TooFast()
```

The expression after `else` runs only when the check fails. It can return a
named error constructor or an error variable. `else` marks the failure path.

## Offer several acceptable checks with `or`

Use `or` to join several constraint chains on the same value.

```ft
ensure password is Strong() or Passkey() else InvalidCredential()
```

This check passes when `password` satisfies either `Strong()` or `Passkey()`.
`or` joins alternative conditions on one value. It is not boolean `||`.

## Check against a named type

A bare name after `is` checks membership in a named type instead of calling an
assertion.

```ft
ensure status is ActiveStatus else InvalidStatus()
```

`ActiveStatus` has no parentheses. This tells Forst that `ActiveStatus` is a
named type, such as a literal union. Use parentheses for assertion calls like
`Strong()`.

Enum variants are not assertions. Define a named subset type when a function accepts
only specific enum members.

## Exiting from `main`

`main` starts the process. A failed `ensure` there ends the process with exit
status 1. There is no caller to return an error to, so a typed `else` is not allowed.

Write `ensure !err` when you only need that exit. Add `else { ... }` when
you want to log or clean up first. The block runs on failure. The process
still exits afterward.

This example calls `drive`, then `stop`. The first check has no block. The
second prints a line if `stop` fails.

<EnsureMain />

If `drive` fails, the program writes to stderr and exits. `stop` never runs.
If `stop` fails, the program prints `failed to stop:` and the error, then
exits. Nothing after that `ensure` in `main` runs.

## Check for missing values

Use `Nil()` when a value must be absent. This works with nilable values such as
pointers, `Map`, `Array`, and `Error`.

<EnsureNil />

`claim` continues only when `slot` is nil, then stores `value` there. `open`
then uses `ensure !err`, the short form of `ensure err is Nil()`, and returns
the occupied value. When the checked value
has type `Error`, a failed check implicitly returns that error from a non-`main`
function. In other words, both forms behave like `ensure !err else err` and
lower to the same Go `if err != nil { return err }` check.

This propagation is specific to errors. A bare `Nil()` check on a pointer, map,
or array still produces the normal assertion error because the checked value is
not itself returnable as an error. Add an explicit `else` whenever you want a
different failure value.

Pointer fields also support
[`.Present()` and `.Nil()`](/language/shapes-and-constraints). Full optional
value types such as `T | Nil` are still [planned](/resources/roadmap).

## Use a successful Result value

Map lookups and other operations that may fail return `Result(V, Error)`.
Check for `Ok()` before using the successful value.

<EnsureCatalog />

After `ensure avail is Ok()`, `avail` has the value type stored in the map. The
next check can safely compare the requested quantity with it.

Use the same pattern for function calls that return a `Result`.

## Choose a branch after a check

Use `if x is ...` when both outcomes belong in the current function. Forst
refines the value inside the matching branch.

The original type remains available outside the branch.

## How refinements survive mutation

A successful check establishes a refined fact about a specific storage path. Forst
remembers that fact on later lines so you do not need to re-validate the value
before passing it to functions that require it.

```ft
type Order = {
    address: Address,
    lastViewedAt: Int,
    amount: Int,
}

type Address = {
    country: String,
}

is (order Order) Shippable() {
    ensure order.address.country is Present()
}

func ship(order Order) {
    // Requires order to be Shippable
}
```

### Establish and reuse a refinement

Check the order once before calling operations that need a valid destination.

```ft
ensure order is Shippable() else CannotShip()
ship(order)
```

`ship(order)` runs without re-checking `order.address.country`. The compiler
knows that `order` satisfied `Shippable()` on the earlier line.

### What invalidates a refinement

Writing to a field that a check depends on invalidates that refinement.

```ft
ensure order is Shippable() else CannotShip()
order.address.country = nil
ship(order) // Error: order no longer satisfies Shippable
```

The write `order.address.country = nil` is legal. It invalidates `Shippable`
because country data was modified. The compiler points out the invalidated check at
`ship(order)`, showing:

- the dropped condition name (`Shippable`);
- the line where it was established;
- the write that invalidated it;
- how to restore it (`ensure order is Shippable()`).

Re-`ensure` the value after changing dependent fields to restore the refinement.

### What keeps a refinement intact

Writes to unrelated fields leave existing refined facts intact.

```ft
ensure order is Shippable() else CannotShip()
order.lastViewedAt = 1700000000
ship(order) // Still valid: lastViewedAt is not a dependency of Shippable
```

Reading a field never invalidates a refinement.

### Pointer fields and slots

Assigning `nil` directly to a pointer slot (`order.address = nil`) drops
presence facts on `address` and its child fields. Writing a field through an
existing pointer (`order.address.country = "US"`) modifies the pointee value but
does not clear pointer presence on `address`.

## Keep checks explicit

Forst keeps validation visible in normal control flow. `ensure` returns an
error. `if` selects a branch. Values are never silently coerced.

This avoids common problems from other approaches.

| Approach | Drawback |
| --- | --- |
| A single value Go assertion such as `x.(T)` | Can panic when the value has another type |
| A TypeScript assertion such as `value as T` | Bypasses runtime validation |
| Exceptions | Move failure handling away from the check |

## Current limits

`ensure` and narrowing are actively expanding. See the [roadmap](/resources/roadmap).

### Control flow joins and loops

A refinement survives a branch split (`if` / `else`) only when it holds on every
path. Loops assume zero iterations may run, so facts established inside a loop
body do not leak past the loop unless proven invariant.

### Function calls and Go interop

Calling a Forst function that mutates a dependency path invalidates refined facts on that
path. Calls to untrusted Go packages, `unsafe`, or `reflect` conservatively drop
facts on reachable mutable arguments, but the call itself remains legal.

### Aliases and concurrency

Writing through a pointer alias (`alias := &order; alias.address.country = nil`)
drops facts on the aliased value. Spawning a goroutine (`go worker(order)`) or
sending reference bearing data through a channel clears refined facts on shared mutable
storage. Forst uses no borrow checker, ownership syntax, or runtime version tags.

### Map lookups use Result

Forst map lookups return `Result(V, Error)`. Go style comma assignment such as
`v, ok := m[k]` is unsupported. Use `ensure avail is Ok()` before reading the
value.

## Generated Go

Generated Go uses ordinary conditionals and error returns for `ensure`.
A custom failure after `else` becomes a named Go error type. In `main`, a
failed check exits the process instead of returning.
